# Electron 상세 가이드

> 선택 참조 문서다. 반드시 지킬 규칙은 `electron` 팩 본문(`packs.source.json`)에 있고, 이 문서는 그 규칙의 배경과 예시를 필요할 때 읽도록 둔다. 이 문서와 팩 본문이 다르면 팩 본문을 따른다.

## Electron 스택 / 프로세스 권한 경계

### 기반 원칙
- 기존 프로젝트는 `package.json`과 lockfile에 명시된 Electron 버전을 그대로 쓰고, 그 버전 문서에 있는 API만 사용한다. 메이저 업그레이드와 새 의존성 도입은 사용자가 요청했을 때만 진행한다.
- 보안 기준은 Electron 공식 보안 체크리스트(https://www.electronjs.org/docs/latest/tutorial/security)를 따르되, 현재 버전이 지원하는 옵션인지 먼저 확인한다.

### 프로세스 책임
- main: 창과 앱 수명주기, 파일·프로세스·네트워크·OS 접근, 권한 판단을 소유한다.
- preload: main과 renderer 사이의 좁은 API만 노출한다. 비즈니스 로직과 상태를 두지 않는다.
- renderer: 화면과 사용자 상호작용만 담당한다. Node API, 파일 시스템, 자식 프로세스에 직접 접근하지 않는다.

### BrowserWindow / webPreferences
- `contextIsolation: true`, `nodeIntegration: false`를 유지하고 `sandbox`는 기존 설정보다 낮추지 않는다. `webSecurity: false`, `allowRunningInsecureContent`, `experimentalFeatures`, `enableBlinkFeatures`는 켜지 않는다.
- 원격 콘텐츠를 앱 권한(preload API)이 있는 창에 로드하지 않는다. 필요하면 preload 없는 별도 창이나 외부 브라우저로 연다.
- `shell.openExternal`에는 허용한 스킴(`https:` 등)과 검증한 URL만 넘긴다. 사용자 입력이나 원격 문자열을 그대로 넘기지 않는다.
- 창 이동과 새 창 열기는 `will-navigate`, `setWindowOpenHandler`에서 허용 목록만 통과시킨다.
- 권한 요청(카메라, 알림 등)은 `session.setPermissionRequestHandler`에서 필요한 것만 허용한다.
- 앱 화면에는 CSP를 두고, 기존 CSP를 넓히는 변경(`unsafe-eval`, 와일드카드 출처)은 이유를 남긴다.

### preload 노출
- `contextBridge.exposeInMainWorld`로 좁은 API만 노출한다. `ipcRenderer` 자체, 아무 채널이나 무제한 중계하는 `send(channel, ...)`·`invoke(channel, ...)`, Node 모듈 객체를 노출하지 않는다.
- 채널을 엄격한 허용 목록으로 제한한 `invoke`/`on` 래퍼는 허용되는 구조다. 허용 목록은 main 등록 채널과 테스트로 맞춘다.
- 이벤트 구독 API는 해제 함수를 반환하고, renderer 콜백에 `IpcRendererEvent`(sender 포함)를 넘기지 않는다.
- preload 노출 API, renderer 전역 타입 선언, main 핸들러, 호출자는 같은 변경에서 함께 갱신한다.

## IPC 계약과 검증

### 채널 / DTO 동기화
- 채널 이름은 `domain:action` 형태로 정하고 상수나 허용 목록 한 곳에서 관리한다. preload 허용 목록과 main 등록 목록이 어긋나지 않는지 테스트로 확인한다.
- 요청·응답 DTO는 공유 타입이나 스키마 하나로 정의하고 main·preload·renderer가 같은 정의를 따른다. 필드를 바꾸면 세 계층과 테스트를 함께 바꾼다.
- 응답 형태는 채널 계층 안에서 통일한다(예: `{ success, data?, error? }`). 예외 객체나 내부 스택을 그대로 renderer로 넘기지 않는다.
- 구조화 복제가 가능한 평범한 데이터만 주고받는다. 함수, 클래스 인스턴스, 순환 참조를 보내지 않는다.

### 송신자와 입력 검증
- 권한이 필요한 `ipcMain.handle`/`ipcMain.on` 핸들러는 `event.senderFrame`(또는 `event.sender`)이 예상한 앱 창과 출처에서 왔는지 확인하고, 그렇지 않으면 거절한다.
- renderer가 보낸 값은 신뢰하지 않는다. 타입, 필수 필드, 길이, 허용 값을 핸들러 가까이에서 검증한 뒤 사용한다.
- 경로 인자는 정규화한 뒤 허용된 기준 디렉터리(사용자가 고른 프로젝트, 앱 데이터 폴더) 안인지 확인한다.
- renderer 입력으로 셸 명령 문자열을 조립하지 않는다. 실행 파일과 인자 배열을 분리하고 허용 목록으로 제한한다.
- 같은 채널을 두 번 등록하지 않는다. 다시 등록해야 하면 `removeHandler`/`removeListener` 뒤에 등록한다.

### main에서 renderer로 보내는 이벤트
- 보내기 전에 대상 `webContents`가 파기되지 않았는지(`isDestroyed()`) 확인한다.
- 이벤트에 세션 ID, 실행 ID 같은 대상 식별자를 넣어 renderer가 현재 화면과 무관한 늦은 이벤트를 버릴 수 있게 한다.
- 로그나 토큰 스트리밍 같은 고빈도 이벤트는 묶어서 보내거나 빈도를 제한해 renderer가 멈추지 않게 한다.

## main 비차단 / 자식 프로세스 / 리소스 수명

### main 비차단
- 사용자 동작 경로의 main 코드에 `*Sync` 파일·프로세스 API, 큰 JSON 파싱, CPU 집약 작업을 두지 않는다. 비동기 API, 지연 로딩, worker나 utility process를 사용한다.
- 앱 시작 경로에는 첫 창 표시에 필요한 일만 둔다. 무거운 모듈과 백그라운드 작업은 창 표시 뒤로 미룬다.
- 오래 걸리는 작업은 진행 이벤트와 취소 수단을 제공하고, 한 IPC 핸들러가 끝날 때까지 다른 요청이 막히지 않게 한다.

### 자식 프로세스 소유와 종료
- `spawn`/`execFile`로 만든 프로세스는 세션이나 작업 같은 실행 단위가 소유한다. 소유자가 핸들을 보관하고 종료·정리 책임을 진다.
- `shell: true`나 `exec`에 외부 입력을 넣지 않는다. Windows `.cmd` shim처럼 셸 실행이 필요하면 인자를 검증하고 이스케이프한다.
- `exit`·`close`·`error`는 하나의 완료 경로로 모아 한 번만 처리한다. 타임아웃은 이름 있는 상수로 두고, 초과하면 종료 요청 → 유예 → 강제 종료 순으로 처리한다.
- Windows에서는 부모 프로세스만 먼저 종료하면 `.cmd` shim이나 CLI가 띄운 손자 프로세스가 고아로 남을 수 있다. 종료 대상은 소유한 프로세스 트리 전체로 잡고(예: 트리 단위 종료), 종료 뒤 트리에 남은 프로세스가 없는지 확인한다. 종료를 위해 권한을 올리거나 기존 권한·샌드박스 설정을 완화하지 않는다.
- 중단과 완료는 경쟁할 수 있다고 가정한다. 중단 요청 뒤에 도착한 출력이나 종료 코드로 상태를 성공으로 바꾸지 않고, 이미 끝난 프로세스에 대한 중단 요청은 무해하게 처리한다.
- 앱 종료(`before-quit`, `will-quit`)와 창 파기 때 소유한 자식 프로세스를 정리한다. 정리 경로가 `app.quit()`을 다시 불러 재귀 루프에 빠지지 않게 한다.
- stdout·stderr는 끝까지 소비하거나 버퍼 상한을 둔다. 로그에 비밀값과 전체 사용자 경로를 남기지 않는다.

### 리스너 / 타이머 / 창
- `app`, `BrowserWindow`, `webContents`, `ipcMain`, `powerMonitor`에 건 리스너와 `setInterval`·`setTimeout`은 소유 객체가 파기될 때 해제한다.
- 창 참조는 `closed` 이벤트에서 비우고, 파기된 창에 접근하지 않는다.
- 단일 인스턴스 잠금, 트레이, 전역 단축키처럼 앱 전역 자원은 한 모듈이 등록과 해제를 소유한다.

### 실행별 정책 소유
- 권한, 샌드박스, 모델, 작업 디렉터리 같은 실행 정책은 실행을 시작할 때 확정해 실행 객체에 묶는다. 실행 도중 전역 설정이 바뀌어도 진행 중인 실행의 정책은 바뀌지 않게 한다.
- 정책 판단은 main에서 한다. renderer가 보낸 정책 값은 요청으로만 보고 main에서 허용 범위를 다시 확인한다.

## 설정 / 기록 / 비밀 분리와 테스트

### 저장 데이터 분리
- 사용자 설정, 실행 기록(로그, 히스토리, DB), 비밀값(토큰, API 키, 비밀번호)은 서로 다른 저장소에 둔다. 설정 파일이나 기록에 비밀값을 섞지 않는다.
- 비밀값은 OS 자격 증명 저장소나 `safeStorage` 같은 암호화 경로에 둔다. renderer에는 비밀값 대신 존재 여부나 마스킹된 값만 넘긴다.
- 앱 데이터 위치는 `app.getPath('userData')` 같은 Electron 경로 API로 정하고 사용자 경로를 하드코딩하지 않는다.
- 저장 형식을 바꿀 때는 기존 사용자 데이터를 읽어 옮기는 경로를 두고, 옮기다 실패해도 원본을 지우지 않는다.
- 설정 쓰기는 임시 파일에 쓴 뒤 교체하는 방식처럼 중간 실패로 파일이 깨지지 않게 한다.

### 테스트
- main 로직은 `app`, `BrowserWindow`, `ipcMain` 같은 Electron 객체와 분리된 모듈로 두어 Electron 없이 테스트한다. Electron 객체는 얇은 가짜 객체로 대체한다.
- 파일·설정·DB 테스트는 임시 디렉터리를 userData·홈 경로로 주입해 실제 사용자 데이터와 사용자 전역 설정(`~/.claude`, `~/.codex` 등)을 건드리지 않는다. 테스트가 끝나면 임시 디렉터리를 정리한다.
- IPC 핸들러 테스트는 정상 입력과 함께 잘못된 타입, 허용되지 않은 경로, 예상하지 못한 송신자를 다룬다.
- 자식 프로세스 테스트는 가짜 실행 파일로 정상 종료, 실패 종료, 타임아웃, 중단과 완료의 경쟁을 검증하고, 끝난 뒤 남은 프로세스와 타이머가 없는지 확인한다.
- preload 허용 채널과 main 등록 채널의 일치처럼 여러 파일이 맞춰야 하는 계약은 정적 검사 테스트로 고정한다.

### 완료 전 필수 검문
- 새 IPC 핸들러에 송신자 확인과 입력 검증이 있는지 확인한다.
- preload, renderer 타입 선언, main 핸들러, 호출자를 함께 갱신했는지 확인한다.
- 새로 만든 자식 프로세스·리스너·타이머에 종료와 해제 경로가 있는지 확인한다.
- webPreferences 보안 옵션을 낮추지 않았는지 확인한다.
- 테스트가 실제 userData나 사용자 전역 설정에 쓰지 않는지 확인한다.
