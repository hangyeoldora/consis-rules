# 클린 코드 공통 상세 가이드

> 선택 참조 문서다. 반드시 지킬 규칙은 `clean-code` 팩 본문(`packs.source.json`)에 있고, 이 문서는 그 규칙의 배경과 예시를 필요할 때 읽도록 둔다. 이 문서와 팩 본문이 다르면 팩 본문을 따른다.

## 책임과 부수효과 경계

### 단일 책임
- 함수·모듈을 나누는 기준은 줄 수가 아니라 변경 이유다. 길어도 한 흐름을 위에서 아래로 읽을 수 있으면 억지로 쪼개지 않는다.
- 한 함수가 입력 해석, 정책 판단, 저장·전송, 화면 갱신을 함께 하면 판단(순수 계산)과 실행(I/O)을 분리한다.
- 새 이름은 무엇을 결정하거나 수행하는지 드러낸다. `handle`, `process`, `doWork`, `util`처럼 책임이 드러나지 않는 이름을 새로 만들지 않는다.
- `utils`, `helpers`, `common`에 도메인 판단을 쌓지 않는다. 쓰는 곳 가까이에 두고, 두 곳 이상이 같은 규칙으로 쓸 때만 올린다.

### 부수효과 경계
- 파일·네트워크·DB·프로세스·시계·난수·환경 변수 접근은 경계 모듈에 모으고, 핵심 로직은 값을 받아 값을 돌려주게 만든다.
- 조회처럼 보이는 함수(`get*`, `find*`, `is*`, `has*`)에서 쓰기, 캐시 무효화, 이벤트 발행 같은 숨은 부수효과를 만들지 않는다.
- 부수효과 순서가 계약이면(저장 후 알림, 잠금 후 쓰기) 한 함수 안에 순서를 명시하고 여러 곳에 흩어놓지 않는다.
- 모듈을 import하는 것만으로 프로세스 실행, 파일 쓰기, 타이머 시작, 전역 등록이 일어나지 않게 한다. 명시적 초기화 함수로 옮긴다.

### 실패 처리
- 실패를 삼켜 성공으로 위장하지 않는다. 빈 `catch`, 로그만 남기고 성공처럼 반환하는 처리를 금지하고, 복구할 수 없으면 호출자가 판단할 수 있는 형태로 올린다.
- 의도된 best-effort 정리(이미 닫힌 핸들 정리, 임시 파일 삭제 실패 무시 등)나 "없으면 빈 값"처럼 명시된 정상 계약은 예외다. 이때는 무시하는 실패의 범위를 좁게 한정한다.
- 실패 표현(예외, `{ ok: false }` 같은 결과 객체, `null`)은 한 계층 안에서 하나로 통일한다. 같은 함수가 상황마다 다른 방식을 섞지 않는다.
- 경계 밖(사용자, 외부 시스템)으로 나가는 오류는 원인을 보존해 기록하되 메시지에 비밀값, 전체 경로, 원문 데이터를 넣지 않는다.

## 타입, 입력 검증, 상태 소유

### 명시적 타입과 계약
- 공개 함수, 모듈 경계, 직렬화되는 데이터(IPC, API, 파일, DB 행)는 타입이나 스키마로 형태를 명시한다. JS 프로젝트는 JSDoc이나 기존 검증 방식을 따른다.
- 근거 없는 타입 우회(`any`, `as`, `!`, 캐스팅)로 타입 오류를 덮지 않는다. 타입 가드나 검증 후 변환으로 해결하고, 외부 라이브러리 타입 한계처럼 근거가 있을 때만 가장 좁은 범위에서 쓴다.
- 문자열 상태값은 유니온이나 열거형으로 묶고 분기에서 모든 경우를 처리한다. 가능하면 누락을 컴파일·테스트 단계에서 잡는다.
- 서로 배타적인 상태를 불리언 플래그 여러 개로 표현하지 않는다(`isLoading && isError` 같은 불가능한 조합). 단일 상태 필드로 표현한다.

### 입력 검증
- 신뢰 경계(사용자 입력, 다른 프로세스, 네트워크, 파일, 환경 변수)를 넘은 값은 경계에서 한 번 검증하고 내부에는 검증된 값만 넘긴다.
- 허용 목록 방식으로 검증한다. 타입, 필수 여부, 길이·범위, 허용 값을 확인하고, 경로라면 정규화 후 기준 디렉터리 안인지까지 확인한다.
- 검증 실패를 기본값으로 조용히 대체하지 않는다. 기본값이 계약일 때만 대체하고, 그 외에는 명시적 오류로 돌려준다.
- 같은 검증을 호출 경로마다 복사하지 않는다. 경계에 검증 함수를 하나 두고 재사용한다.

### 상태 소유
- 상태마다 쓰기 소유자를 하나로 정한다. 다른 모듈은 읽기 API나 이벤트로만 접근하고 직접 변경하지 않는다.
- 다른 값에서 계산할 수 있는 값은 상태로 따로 저장하지 않는다. 캐시가 필요하면 무효화 조건을 함께 둔다.
- 모듈 전역 가변 상태는 피한다. 불가피하면 소유 모듈 안에 숨기고 초기화·리셋 경로(테스트 포함)를 둔다.
- 요청, 세션, 작업 같은 실행 단위의 상태는 그 실행 객체에 묶어 이전 실행의 값이 다음 실행으로 새지 않게 한다.

## 비동기 취소와 리소스 정리

### 취소와 늦은 이벤트
- 오래 걸리는 비동기 작업은 취소 수단(`AbortSignal`, 취소 토큰, 실행 ID)을 받고, 취소된 뒤에는 결과를 반영하지 않는다.
- 응답이나 이벤트가 도착하면 현재 실행의 것인지 확인한다(실행 ID, 세대 번호, 대상 ID 비교). 이미 끝났거나 교체된 실행의 늦은 결과로 상태를 덮어쓰지 않는다.
- 완료·실패·취소·타임아웃은 하나의 종료 경로로 모아 한 번만 처리한다. 중복 resolve/reject와 이중 정리를 막는다.
- `await` 사이에는 상태가 바뀔 수 있다고 가정한다. `await` 뒤에는 대상(창, 컴포넌트, 세션, 연결)이 아직 유효한지 다시 확인한다.

### 비동기 오류
- 만든 Promise는 `await`하거나 반환한다. 의도적으로 떼어낼 때는 `.catch`로 오류를 처리해 처리되지 않은 rejection을 남기지 않는다.
- 독립 작업을 병렬로 실행할 때는 `Promise.all`이나 `Promise.allSettled`로 묶고, 일부가 실패하면 나머지를 어떻게 할지 정한다.
- 재시도는 멱등 작업에만 적용하고, 횟수와 backoff 상한을 이름 있는 상수로 둔다.

### 리소스 수명
- 타이머, 이벤트 리스너, 구독, 파일 핸들, 자식 프로세스, watcher는 만든 쪽이 정리한다. 생성 코드 가까이에 해제 경로를 함께 둔다.
- 정리는 성공·실패·취소 모든 경로에서 실행되게 `finally`, dispose 함수, cleanup 반환으로 보장한다.
- 같은 대상에 리스너를 반복 등록하지 않는다. 다시 등록해야 하면 기존 리스너를 먼저 해제한다.
- 타임아웃과 한도(재시도 횟수, 버퍼 크기, 동시 실행 수)는 이름 있는 상수로 둔다.

## 중복 제거, 작은 리팩터링, 의미 있는 검사

### 중복 제거
- 같은 이유로 함께 바뀌는 코드가 두 곳 이상 반복될 때 합친다. 모양만 비슷하고 바뀌는 이유가 다르면 합치지 않는다.
- 상수, 채널 이름, 스키마, 상태값 목록처럼 여러 곳이 맞춰야 하는 값은 한 곳에서 정의하고 가져다 쓴다.
- 복사본이 필요한 데이터나 문서는 원본을 하나로 정하고, 사본은 생성하거나 동일성을 테스트로 확인한다.

### 행동을 유지하는 작은 리팩터링
- 리팩터링은 동작 변경 없이 한 번에 한 유형만 한다. 이름 변경, 추출, 이동, 중복 제거를 섞지 않고 기능 변경과 같은 커밋에 섞지 않는다.
- 테스트가 없는 코드는 현재 동작을 고정하는 테스트를 먼저 추가한 뒤 바꾼다.
- 요청 범위 밖에서 발견한 개선점은 바로 고치지 않고 보고한다.
- 줄 수, 함수 길이, 파일 크기만을 근거로 분리하거나 추상화하지 않는다. 분리한 뒤 읽기와 테스트가 실제로 쉬워지는지로 판단한다.

### 의미 있는 검사
- 테스트는 바뀐 계약을 검증한다. 경계값, 잘못된 입력, 실패·취소·타임아웃, 늦은 이벤트처럼 실제로 깨질 수 있는 경로를 포함한다.
- 내부 호출 순서나 private 함수보다 관찰 가능한 결과(반환값, 저장된 상태, 발행된 이벤트, 남은 리소스)를 검증한다.
- 항상 통과하는 테스트, 스냅샷만 갱신하는 테스트, mock 호출 자체만 확인하는 테스트를 추가하지 않는다.
- 테스트는 서로 독립적으로 실행되게 하고, 임시 디렉터리·가짜 시계·테스트 전용 설정으로 사용자 환경과 실제 데이터를 건드리지 않는다.

### 완료 전 필수 검문
- 분리한 함수·모듈이 줄 수가 아니라 변경 이유 기준으로 나뉘었는지 확인한다.
- 신뢰 경계 입력을 검증했는지, 실패를 삼킨 곳이 없는지 확인한다.
- 새로 만든 타이머·리스너·프로세스·구독에 해제 경로가 있는지 확인한다.
- 늦게 도착한 비동기 결과가 현재 상태를 덮어쓸 수 없는지 확인한다.
